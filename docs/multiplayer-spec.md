## 0. Итог в одном абзаце

Текущая архитектура (авторитетный сервер, чистый TS-движок, тупой клиент-рендер) — **правильный фундамент** для мультиплеера и уже частично анти-чит-совместима. Но `GameSession` спроектирован как «1 WebSocket-соединение = 1 игра = 1 герой + 19 ботов», без: реального ввода игрока, персистентности, лобби, устойчивости к разрывам сети и без protocol-уровня для нескольких людей в одной сессии. Это не косметика — это структурные ограничения, которые надо убрать до того, как писать лобби/матчмейкинг.

## 1. Критические проблемы (блокируют мультиплеер и/или кросс-платформу)

### 1.1 Архитектурные — блокируют мультиплеер напрямую

**P1. `GameSession` жёстко привязана к одному WS-соединению = одному человеку.**
`session.ts` держит состояние гонки на одно `hello(PilotProfile)`, один герой среди 19 ботов. Чтобы посадить N живых игроков в одну гонку, нужно:
- Отвязать `GameSession` от конкретного соединения: сессия — это комната (room) с картой `connectionId → driverId`, а не 1:1.
- Broadcast `snapshot()` всем участникам комнаты, а не return одному сокету.
- Разделить «создание гонки» (`hello` → бронирование слота в решётке) и «подключение к уже идущей комнате» (реконнект/зритель).

**P2. `reactionTimeSec` героя захардкожен (`session.ts:66`, значение 0.2).**
Стартовый мини-гейм не подключён к вводу. Для мультиплеера это критично вдвойне: реальная реакция игрока должна прийти по сети *до* дедлайна старта, с защитой от читов (см. P6) и с учётом сетевой задержки (иначе игрок с лучшим пингом получает системное преимущество на старте). Нужен отдельный протокольный этап "lights out" с явным окном приёма ввода и server-side timestamp, а не client timestamp.

**P3. Управление скоростью симуляции (`speed 1–30`, `pause`) — не масштабируется на несколько игроков.**
Сейчас `speed`/`pause` — команды клиента, применяемые к сессии целиком (single-player QoL: перемотка/пауза). В комнате с несколькими живыми людьми это должно исчезнуть или стать admin-only/спектатор-режимом — иначе один игрок может поставить гонку на паузу или ускорить/замедлить её для всех. Нужно явно развести: **race speed управляется только сервером в реальном времени** (fixed dt=0.1s), а «ускорение x2/x6/x12/x24» на клиенте (`RaceView.tsx`) остаётся локальным UI-предпросмотром для single-player/replay и должно быть выключено в PvP-комнатах.

**P4. Синие флаги через «телепортацию» лидера (`engine.ts:391`, `other.s = ...` — двигается именно лидер, не отстающий).**
Костыль, незаметный при одном человеке за экраном. При нескольких живых наблюдателях телепортация машины будет выглядеть как явный баг/дисконнект и создаст ощущение рассинхрона. Проблема глубже, чем просто «плохой частный случай»: модель обгонов (`passProbability`) вообще не различает машины на разных кругах — отсюда и потребность в грубом телепорте, чтобы развести трафик. Правильный фикс — завести lap-delta в контекст боя (`handleBattles`) и обрабатывать круговых через pace-модулятор («yield»-поведение, отстающий по кругу снижает целевую скорость сам, без ручной правки позиции лидера), а не патчить симптом точечной телепортацией.

### 1.2 Сеть/протокол — блокируют кросс-платформу и стабильность

**P5. Нет reconnection-протокола.**
`protocol.ts` не описывает поведение при разрыве соединения (мобильная сеть — норма, не исключение). Нужны: session token, буфер последних N снапшотов/дельт для быстрого ресинка, grace period перед тем как считать игрока сдавшимся (DNF), явные сообщения `reconnect`/`resume`.

**P6. Нет валидации/rate-limit на клиентские команды.**
`pit { compound }`, будущий ввод реакции на старте, `restart` — всё это должно валидироваться на сервере (частота сообщений, допустимые окна по времени гонки, соответствие `driverId` отправителю сокета). Сейчас документ явно фиксирует принцип «клиент — тупой рендер», но нет описания server-side проверки *входящих* команд, только раздачи снапшотов наружу. Для мультиплеера с реальными людьми это открытая дыра под простой DoS/спам-команды или манипуляцию гонкой других игроков, если `driverId` не проверяется на серверной стороне сокета.

**P7. Snapshot — полный (full-state), не дельта.**
Для web с нескольким полем в 20 машин это ок, но для кросс-платформы (мобильные сети, экономия трафика) полный снапшот 10×/сек на клиента будет дорогим. Нужен переход на delta-encoding или явное разграничение "full snapshot on join" + "delta 10 Гц" в проекте протокола.

### 1.3 Данные/персистентность — блокируют кросс-платформу напрямую

**P8. Нет авторизации и сохранения персонажа (пункт роадмапа #1, но это не «фича», а предпосылка кросс-платформы).**
Без аккаунта нет смысла говорить о «кросс-платформе» — прогресс должен переживать переход web↔mobile↔desktop. Это должно идти **раньше** мультиплеера в очереди работ, потому что лобби/матчмейкинг (роадмап #2) без identity не имеют смысла (кого матчить?).

**P9. XP/уровни/дивизионы посчитаны, но не вызываются нигде (`config.ts`).**
Формулы есть, но результат гонки нигде не пишется в постоянное хранилище. Для кросс-платформенной игры это первая вещь, которая должна связаться с БД, иначе прогрессия — фейковая механика.

**P10. In-memory state сервера — единая точка отказа.**
`GameSession` живёт только в памяти процесса. Рестарт сервера = потеря всех активных гонок. Это терпимо для single-player прототипа, но не для мультиплеера с реальными людьми в комнате — нужен хотя бы periodic snapshot состояния сессии во внешнее хранилище (Redis/аналог) для recovery, и это же — предпосылка горизонтального масштабирования (несколько инстансов сервера, session affinity или переезд сессии).

### 1.4 Тесты/процесс — блокируют безопасный рефакторинг

**P11. Нет тестов для `apps/server` и `apps/web` (только `race-engine` — 34 vitest-теста).**
Переход к мультиплееру — это рефакторинг именно `session.ts`/`protocol.ts`/сетевого слоя, то есть ровно той части, которая не покрыта тестами. Делать это без хотя бы integration-тестов на WS-протокол — высокий риск регрессий, которые не поймает существующий `pnpm --filter @f1race/race-engine test`.

**P12. Нет remote/CI.**
Ни удалённого репозитория, ни пайплайнов. Для командной разработки мультиплеера (несколько агентов/разработчиков параллельно трогают server/protocol) это блокер сам по себе — нет проверки, что чужой PR не сломал сборку или существующие 34 теста.

### 1.5 Прочее, нашёл попутно (не блокер, но стоит зафиксировать)

**P13. Юридический риск.** Имена/страны/команды — «захардкоженные списки из 20 реальных пилотов» и реальные команды Ф1. Для прототипа/локальной игры это ок, но при выходе на публичный мультиплеер (тем более кросс-платформенный релиз в сторах) — это использование реальных имён/брендов без лицензии. Стоит заранее спроектировать слой абстракции «driver profile / team skin» так, чтобы данные легко заменялись на вымышленные или лицензионные.

**P14. Одна трасса (Red Bull Ring).** Не блокер архитектурно (`track.ts` уже параметризован сегментами), но для мультиплеерного пула матчей нужен минимум 2-3 трассы, иначе матчмейкинг тривиален, а реиграбельность низкая.

**P15. DRS определён (`drsGapSec: 0.5`), но не используется в `passProbability`.** Незавершённая фича — стоит либо доделать, либо явно вычеркнуть из config, чтобы не путать следующего агента мёртвым полем.

### 1.6 Пропущено в первой версии спеки (добавлено по итогам ревью)

**P16. Нет клиентской интерполяции/буфера снапшотов.**
`TrackCanvas` сейчас рендерит последний полученный снапшот напрямую. Для single-player по локальной сети джиттер незаметен, но в реальном мультиплеере (тем более на мобильных сетях) это даст видимые рывки машин. Это важнее для ощущения качества, чем delta-encoding (P7): нужен render-behind буфер — интерполяция позиции между двумя последними снапшотами, рендер с намеренной задержкой ~100 мс от «настоящего времени», а не мгновенный snap к последним данным.

**P17. Не зафиксирована семантика опоздавших/пограничных команд.**
Например, `tryAutoPit`/ручной `requestPit` проверяют близость к `pitEntryS` — команда, пришедшая не в окно, по факту откладывается до следующего круга. Это разумное поведение уже есть в движке, но оно нигде не описано как протокольный контракт. Для мультиплеерной честности это должно быть явным правилом: «команда, пришедшая вне применимого окна, не отбрасывается молча и не выполняется мгновенно — она встаёт в ожидание следующего валидного окна», и клиент должен это в UI показывать (иначе игрок решит, что клик не сработал). Это отдельная тема от валидации доступа (P6) — там про «кто может слать», здесь про «когда команда физически применяется».

**P18. Нет основы для детерминизма/реплея.**
В движке уже есть `mulberry32(seed)` — это почти бесплатная страховка, которую сейчас никто не использует. Модель «(seed, последовательность входов игроков) → детерминированный результат» даёт: (а) дешёвые реплеи без хранения полного снапшот-потока, (б) базовый анти-чит-инструмент (сервер может пересчитать гонку офлайн и сверить с тем, что разослал онлайн, если когда-то понадобится независимая проверка спорных ситуаций), (в) тестовый примитив «тот же seed + те же inputs = тот же результат» — само по себе полезный regression-тест для race-engine при любом будущем рефакторинге физики.

**P19a. `onCancel` в `PitPanel.tsx:76` — пустышка (`() => {}`).**
`engine.cancelPit` существует, но не проброшен через `session`/`protocol`. Отменить уже запрошенный пит нельзя вообще — это pre-existing баг, никак не связанный с мультиплеером, но становящийся заметнее в PvP, где управляемость решения важнее (например, соперник неожиданно не заехал в пит, и игрок хочет отменить свой запрос под undercut). Правка: прокинуть `cancelPit` через протокол независимо от остального плана по мультиплееру — это баг-фикс, не архитектурная работа.

**P19b. Silent rejection пит-запроса.**
`engine.ts:147` — попытка запросить тот же состав, что уже стоит, молча игнорируется через ранний `return`, `protocol.ts` не отправляет об этом ошибку обратно клиенту. В single-player это не заметно (игрок видит на UI задизейбленную кнопку и просто не кликает), но серверная защита должна быть независимой от UI и видимой: если запрос отклонён (тот же состав, невалидный `driverId`, что угодно ещё) — нужен явный `error`-ответ (тип уже есть в `ServerMessage`), а не тишина. Плюс отдельно зафиксировать модель ёмкости пит-лейн: «8 боксов» в `TrackCanvas.tsx:120-126` — чисто визуальный элемент, в `engine.ts` никакого ограничения нет. Рекомендация: оставить неограниченным ресурсом (декорация), потому что моделирование реальной коллизии/очереди в боксах — это новая игровая механика, а не фикс существующего поведения, и она не нужна, чтобы закрыть P19b.

**P19c. (Вычеркнуто по итогам повторной проверки кода.) Компенсация RTT для окна пит-въезда — не нужна.**
Первая версия P19 ошибочно приравнивала пит-запрос к стартовой реакции (P2): предполагалось, что игрок с большим пингом «промахивается» мимо окна `pitEntryS ± 50м`. Это неверно: `requestPit` (`engine.ts:145`) складирует запрос в очередь (`pitRequests`), а `tryAutoPit` (`engine.ts:267-302`) срабатывает по физическому приближению к воротам на *каждом* шаге симуляции — не важно, послан клик за три круга или за секунду до входа. Окна на клик нет, есть очередь, поэтому пинг здесь не съедает никакого дедлайна: единственная цена позднего клика — не более одного лишнего круга на изношенной резине, и это смягчается заранее показанным в UI износом (уже есть в `PitPanel`), а не сетевой компенсацией. По той же причине неверным было и утверждение про «схлопывание undercut-окна сетью»: круг ~80с, сетевая задержка 200-500мс — это <1% круга, а событие `pit_stop` доставляется тем же 10Гц снапшот-потоком (`snapshot.events`), что и всё остальное — отдельного канала/бюджета задержки под конкретное событие не нужно, это относится к общему P7/P16 (частота и плавность снапшотов), не к питам отдельно.

## 2. Приоритизация: что блокирует что

**Исправлено после ревью:** `Room` — низкоуровневый примитив, `Лобби` над ним, а не наоборот (матчмейкинг *раскладывает игроков по комнатам*, значит комната должна уметь существовать раньше матчмейкинга). Room можно построить и покрыть тестами с гостевой identity (`connectionId → driverId`, без всякого auth) — то есть Room **не зависит** от Фазы Auth, зависит только от Фазы 0 (тесты/CI, детерминизм). Полноценный Auth нужен только там, где нужно *сохранить* прогресс между сессиями/устройствами (P9), и параллельно готовит почву для лобби (нужны стабильные identity, чтобы матчить не гостей-однодневок).

```

         Room-модель (P1) с guest-identity ─────────────────────┐
```

## 4. Изменения в протоколе (`protocol.ts`) — конкретно

Добавить/изменить:
- `Client→Server: joinRoom { roomId, sessionToken }`, `reconnect { sessionToken }`
- `Client→Server: startReaction { clientTimestamp }` — сервер сверяет с собственным окном lights-out, не доверяет clientTimestamp как единственному источнику (использовать его только для UX, а не для расчёта штрафа)

- Убрать/ограничить: `speed`, `pause` — либо только для single-player комнат (`mode: "solo"` vs `mode: "multiplayer"` на уровне комнаты), либо перевести в spectator-only команды

## 5. Предлагаемые фазы разработки

**Фаза 0 — фундамент для безопасного рефакторинга**
- Integration-тесты на `apps/server` (WS handshake, snapshot корректность, reconnection-заглушка)
- CI (даже минимальный: lint + test на push), remote-репозиторий
- Тест на детерминизм движка: «тот же seed + та же последовательность inputs → тот же результат» (P18). Важно: привязывать последовательность inputs к `stepIndex` симуляции, а не к wall-clock времени — иначе тест флапает при разной скорости прогона (например, тестовый харнесс мог бы гонять симуляцию быстрее реального времени, и wall-clock timestamp'ы разъедутся с тем, что видел движок при исходном прогоне)
- `protocolVersion` в `hello` — копеечная добавка сейчас, дорогая, если забыть до первого деплоя новой версии протокола на мобильный клиент
- Переименование захардкоженных реальных пилотов/команд на вымышленные (P13) — дёшево, пока имена не расползлись по UI/тестам/скриншотам
- **P19a** (перенесено сюда из Фазы 2): `onCancel` в `PitPanel.tsx:76` — пустышка, `cancelPit` не проброшен через протокол. Это pre-existing баг, никак не завязанный на мультиплеер — 3-4 строки поверх протокола, нет причины откладывать его до Фазы 2
- **P4** (перенесено сюда из Фазы 6, см. пометку ниже): грубый load-baseline на текущей single-player `GameSession` как приблизительный proxy (сколько активных сессий держит процесс при сегодняшней in-memory модели, до появления Room) — даёт первое число для Q2, уточняется в конце Фазы 1 на реальной Room-модели

**Фаза 1 — Room-модель с гостевой identity (без Auth, без матчмейкинга)**
- `GameSession → Room`: N `connectionId ↔ driverId` (гостевые id, без сохранения), добор ботами, broadcast всем участникам вместо return одному сокету
- Server-side валидация всех входящих команд по `driverId` (P6)
- Reconnection-протокол (P5): session token на уровне комнаты (не аккаунта), grace period, ресинк
- `speed`/`pause` убраны/ограничены до spectator-only в multiplayer-режиме комнаты (P3)
- Явная семантика окон для команд (P17): что происходит с командой, пришедшей вне применимого окна
- **P4** (перенесено сюда из Фазы 6): физически консистентная замена blue-flag телепортации лидера (`engine.ts:391`) через lap-delta в `handleBattles` — правка чисто движковая и не зависит от остального объёма Фазы 1, но её нельзя откладывать до Фазы 6: как только в комнате оказывается больше одного живого человека (то есть с самой Фазы 1), кто-то из них увидит телепортацию как явный визуальный баг/рассинхрон
- **Уточнение load-baseline** (начато в Фазе 0 как proxy): повторный замер на настоящей Room-модели — сколько комнат/гонок держит процесс при broadcast N игрокам вместо return одному сокету; это число закрывает Q2, а не начальная оценка из Фазы 0

**Фаза 2 — Сетевой стартовый мини-гейм**
- Реальный ввод реакции игрока на старте (замена хардкода 0.2), сверка по server timestamp, компенсация лага — единственная часть фазы с реальной сетевой сложностью (timestamp-сверка, fair window, lag compensation); пишется сразу для N игроков в комнате
- Остаток долга по питам (P19b) — silent rejection пит-запроса: добавить явный `error`-ответ вместо тихого игнора, зафиксировать (не реализовывать) решение по ёмкости пит-лейн — оставить неограниченным ресурсом. (P19a уже закрыт в Фазе 0; P19c вычеркнут — RTT-компенсация для питов не нужна, `tryAutoPit` уже решает это очередью, а не таймингом клика)

**Фаза 3 — Identity & Persistence**
- Auth поверх уже работающей Room (email/OAuth — «Яндекс, по образцу alain360» и т.п.; можно начать с более простого провайдера)
- Сохранение `PilotProfile` между сессиями/устройствами, вызов `xpForRace`/`level` в `session.ts` на finish, хранилище (SQLite/`better-sqlite3` на старте — миграция на Postgres тривиальна за интерфейсом; выбор Redis vs файл — по числу из load-baseline Фазы 0)

**Фаза 4 — Лобби и матчмейкинг**
- Тик 30с, добор ботами, дивизионы (используя XP/level из Фазы 3), раскладка игроков по Room из Фазы 1

**Фаза 5 — Кросс-платформенный клиент**
- Вынос `protocol.ts` в общий пакет
- Мобильный клиент (touch-адаптация мини-гейма, PitPanel, canvas DPI) — PWA-first, натив (RN/Skia) только если touch/производительность реально упрутся
- Delta-snapshot протокол (P7) + клиентский interpolation buffer (P16) — второе важнее для ощущения плавности при джиттере

**Фаза 6 — Полировка / контент**
- Ещё 2-3 трассы, Q2/Q3 в квалификации, DRS (P4 закрыт в Фазе 1, не здесь — см. пометку выше)

## 6. Совместимость с будущими фичами вне текущего MVP-плана: 3D-визуализация и RPG-прогрессия пилота

Эти две фичи явно упомянуты как желаемое направление развития, но не входят в Фазы 0-6 (мультиплеер+кросс-платформа). Ниже — оценка архитектурной совместимости, чтобы решения по протоколу/схеме БД в текущих фазах не создавали случайных препятствий для них позже.

### 6.1 3D-визуализация (в дополнение к текущему схематичному виду сверху) — блокеров нет

Сильная сторона текущего дизайна: сервер отдаёт **состояние** (`snapshot()`), а не инструкции по рендеру, и клиент официально зафиксирован как «тупой рендерер» (анти-чит-инвариант). Значит 3D-рендерер — это ещё один подписчик на тот же WS-поток, который серверу не нужно как-либо особо поддерживать. `track.ts` уже существует как чистый геометрический модуль с утилитами интерполяции (`pathPointAt`), переиспользуемый любым рендерером, не только Canvas-версией.

Что придётся **добавить** (аддитивно, без переделки существующего):
1. **Высота/уклон трассы** — сейчас сегменты хранят только `length/targetSpeed`, модель плоская. Elevation/banking — чисто косметический слой данных, не трогает физику (`t0`, `gripFor`, обгоны), можно добавить в любой момент.
2. **Разрешение кривой отдельно от физических сегментов.** 12 физических сегментов — тюнинг-поверхность, дробить их ради визуала нельзя. Path2D из 11 точек, вероятно, недостаточно гладкий для heading машины в повороте в 3D — нужна отдельная плотная кривая только для рендера/ориентации, не завязанная на количество игровых сегментов.
3. **Ориентация машины (yaw)** выводима из касательной трека в точке `s`, новых серверных данных не требует. Но текущий «lateral offset» при обгоне — абстрактный 2D-флаг («машина сейчас смещена вбок»), не полноценная позиция на полосе в метрах — для 3D с объёмным видом рядом идущих машин эту механику, скорее всего, придётся сделать содержательнее.
4. **Частота снапшотов (10 Гц) — этого достаточно** при клиентской интерполяции (см. P16) — стандартная техника для гоночных игр. Ещё один аргумент за то, чтобы не откладывать P16 в конец бэклога. Уточнение: снапшот несёт `sFraction` (`engine.ts:556` — `sNorm / length`, нормированная позиция [0,1)). Для 3D chase-cam этого достаточно, но при интерполяции нормированной дроби на длинных прямых между 10Гц-снапшотами возможны видимые скачки, если позже понадобится показывать соседние машины с субметровой точностью (борьба «бок о бок» в повороте). Не блокер — закрывается тем же P16, но на прямых интерполяция/экстраполяция может потребовать более агрессивной настройки, чем в поворотах — стоит держать в уме, чтобы не расследовать это заново при первой реализации 3D.

Асеты/3D-модели — продакшн-затраты, не архитектурная проблема. Сиквенс: можно делать параллельно/после Фазы 5 (когда протокол снапшотов стабилизировался под кросс-платформу), раньше — нет смысла, второй рендерер будет упираться в ещё меняющийся протокол.

### 6.2 RPG-прогрессия пилота (тренажёрный зал/симулятор, идущий во времени) — блокеров нет, но это отдельная подсистема

Это прямое развитие уже упомянутого в исходном обзоре пункта роадмапа №5 (тренировки/XP/дивизионы посчитаны, но не вызываются — см. P9). Хорошая новость: не нужно изобретать новую систему статов — есть `skills.ts` с 6 навыками и уже провалидированной моделью распределения очков (`validateStartingAllocation`); тренировки логично должны питать те же поля, которые уже используются в формулах движка.

Новое, чего нет в текущем плане мультиплеера:
1. **Асинхронный процесс, переживающий выход игрока из игры.** `GameSession`/будущий `Room` живёт только пока идёт активная гонка — тренировка должна прогрессировать, пока игрока нет онлайн вообще. Нужна отдельная таблица (`trainingId, driverId, startedAt, durationSec, targetStat`) и ленивое вычисление прогресса при следующем заходе игрока (текущее время vs `startedAt + duration`), а не фоновый тикер на каждого офлайн-игрока — второе не масштабируется.
2. **Время — только серверное**, тот же принцип, что и в P6: клиентские часы нельзя использовать как источник правды для «тренировка завершена», иначе тривиально читерится подменой локального времени клиента.
3. **Балансный риск — самое важное здесь.** В кодовой базе уже есть harness'ы (`balance.ts`, `spread.ts`, `stretch.ts`), настроенные под допущение «максимум 5 очков на навык при старте», гарантирующее отсутствие авто-win билдов. Если тренировки дают рост поверх этого без явного потолка — вся протестированная балансировка перестаёт быть гарантией. Нужно осознанное дизайн-решение (потолок роста от тренировок, убывающая отдача, соотношение время/выигрыш) и повторный прогон существующих harness'ов на новом диапазоне значений статов до включения фичи, а не полагаться на то, что старая настройка выдержит сама.
4. **Рассинхрон дивизионов и статов — упущенное дизайн-решение.** Дивизионы (`config.ts:122-126`) завязаны на `level`, который растёт от XP за гонки (`xpToNext`). Тренировки поднимают `skills`, не `level`. Если тренировка даёт статы без XP, `skillSum` и `level` расходятся: игрок может «накачать» навыки до уровня F1, ни разу не выиграв гонку, и наоборот — гонять много, но остаться слабым по статам. Это не косметическая мелочь: от этого напрямую зависит Фаза 4 (по чему матчить — по `level`, по `skillSum`, по гибриду обоих?). Решение нужно принять **до** Фазы 3 — иначе персистентность, введённая в Фазе 3, зафиксирует в БД уже расходящиеся значения, и Фаза 4 унаследует неоднозначную основу для деления на дивизионы, которую придётся чинить задним числом на живых данных игроков.
5. **Стратегический риск для самой цели мультиплеера.** Если idle-тренировка эффективнее по соотношению время/выигрыш, чем реальная гонка за XP, она станет доминантной стратегией — игроки будут «афк-качаться», а не заходить в комнаты. Это не абстрактный баланс-вопрос: он напрямую бьёт по заполняемости мультиплеерных комнат (Фазы 1-4) — то есть по той самой фиче, ради которой весь план и затевался. Решение по потолку/скорости роста тренировок (пункт 3) нужно проверять не только на «нет авто-win билда», но и на «не обесценивает ли это участие в живых гонках».

Зависимость: тренировки требуют Фазы 3 (Auth/Persistence) как предпосылку — без постоянных аккаунтов «прогресс, идущий во времени» физически негде хранить. Ставить эту работу в план стоит после Фазы 3, не раньше.

## 7. Открытые вопросы (нужен ответ до старта Фазы 3-4; Фазы 0-2 от них не зависят)

1. **Целевые платформы.** Прагматичная рекомендация по умолчанию: **PWA-first** — один кодбейс, покрывает web + мобильный браузер сразу, откладывает решение «нужен ли натив» до момента, когда появятся данные о проблемах с производительностью. На Canvas с ~20 машинами натив (React Native/Skia) вряд ли понадобится ради touch-мини-гейма — стоит пересматривать только если профилирование покажет реальную проблему.
2. **Масштаб мультиплеера.** Без ответа P10 нельзя приоритизировать — это не риторический вопрос, а входные данные для Фазы 0 (load-baseline). Ориентир: десятки комнат на инстанс — single-process + периодический Redis-снапшот для recovery достаточен; сотни комнат — нужна принципиально другая архитектура (изоляция состояния между воркерами, симуляция не может упираться в один поток). Число берётся из load-теста Фазы 0, а не назначается заранее.
3. **Хранилище.** SQLite (`better-sqlite3`) на старте — минимум трения, если данные (driver profile, XP, история) спрятаны за интерфейсом репозитория, миграция на Postgres/Redis позже не требует переписывать бизнес-логику.
4. **Юридический статус реальных имён пилотов/команд.** Для закрытой беты — допустимо, но решение должно быть зафиксировано письменно (например, здесь же, с датой и владельцем решения), иначе оно забудется до публичного релиза. Рекомендация по срокам сдвинута из Фазы 6 в Фазу 0 именно потому, что это дешёвая правка сейчас и дорогая — когда имена расползутся по UI, тестам и маркетинговым скриншотам.
5. **По какому полю матчить в Фазе 4: `level`, `skillSum` или гибрид.** Поднимается в 6.2 пункт 4, продублировано сюда как канонический открытый вопрос. `level` растёт от XP за гонки (`xpToNext`), `skillSum` — от (будущих) тренировок. Если тренировки дают статы без XP, поля расходятся, и выбор поля матчинга определяет, что именно игрок может «накачать» idle-тренировкой без выхода в живые гонки. Решение нужно **до** Фазы 3 — иначе персистентность зафиксирует расходящиеся значения в БД, и Фаза 4 унаследует неоднозначную основу для деления на дивизионы. См. также стратегический риск обесценивания живых гонок в 6.2 пункт 5.
