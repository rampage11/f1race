# AGENTS.md

Compact guide for OpenCode sessions working in this repo. Read before running/editing.

## Layout (pnpm workspace)

- `packages/race-engine` — pure TS simulation library (no DOM/Node I/O). `RaceEngine` (race) + `QualifyingEngine` (qualifying). **All formulas/balance live in `src/config.ts`** — this is the single tuning surface. Gameplay systems now modeled there (see "Gameplay systems" below): **Hammer Time** ability in **3 strategic modes** (`HAMMER_TIME` block — `mode.attack/defend/push`, each with its own cornering/overtake/defense/tyreWear; duration 8s, cooldown 45s, blocks on pit/first-lap/tyre-wear≥60%), **weather** (`weather` block — dry/lightRain/heavyRain/variable, **variable raised to 25%** + per-compound grip/wear maps; `TyreCompound` extended with `intermediate`/`wet`), **time-of-day** (`timeOfDay` block — day/sunset/night, cosmetic), **DRS zones + slipstream** (`slipstream` block + `battle.drsPassMultiplier`), **3 tracks** (`redBullRing`/`monza`/`interlagos` in `src/track.ts`, registry `TRACKS` + `randomTrack(rng)`/`trackById(id)`; each `Track` carries `drsZones[]` + `sectors[]`; `segmentIndexAtS` now binary-searches a cached cumulative-length boundary array — O(log n) per lookup), **per-stint push level** (`pace.pushLevel` + `pace.pushWear` blocks — `conservative`/`balanced`/`attack` multipliers on cornering + tyre wear; `RaceEngine.requestPushLevel(driverId, strategy)` sets `car.pushStrategy`/`car.pushLevel` freely; engine resets to `balanced` on fresh-tyre pit exit and the server re-applies the committed strategy post-pit — see "Race control contract"), **mechanical DNF** (`mechanicalFailure` block — ~1%/race per **bot** car; **hero is excluded** — the failure roll is gated on `driver.kind === "bot"` so the player never rage-quits to zero-counterplay RNG; rolled from a dedicated RNG stream so physics stays deterministic), **player-relative bot scaling** (`bots` block — budget = maxHumanSkillSum + divIndex×3 + jitter, bot #1 = +rivalBonus "rival"; `rivalBonus`=6), and **respec gating** (`respec` block — one free at `freeLevel`=4, then `cooldownDays`=30). Tyre grip is now monotonic through the cliff (the cliff branch is anchored at the pre-cliff endpoint `gripFresh×0.97`, no +3% discontinuity). Level curve is `xpToNext = 100 × level^1.3`; level-ups bank `skills.pointsPerLevel` (=2) spendable skill points.
- `apps/server` — Node + WebSocket. Authoritative: runs qualy → startSequence (Phase 2 lights-out mini-game — 5 lights illuminate, then extinguish after a **random** hold via `randomStartDelayMs()` in `start-sequence.ts`; the client illuminates from sequence-receipt, decoupled from `lightsOutAt`) → race, broadcasts `snapshot()`, accepts `hello`/`reconnect`/`pit`/`cancelPit`/`speed`/`pause`/`restart`/`startReaction`/`hammerTime {mode}`/`setStartingTyre`/`setPushLevel {strategy}`/`startTutorial` (first-race tutorial — parallel entry to `hello`, builds a `TutorialRoom`). WS message types live in `src/protocol.ts`; the room loop is `Room` in `src/room.ts` (multi-connection: N clients share one room, broadcast + per-connection `driverId` ownership, session tokens for reconnection, `mode: solo|multiplayer` gating, per-connection rate limits); `restart` is **rejected in multiplayer** (a player can't force a matched room back to qualy). **Each room picks one `track` + `weather` + `timeOfDay` at construction** (sampled from engine CONFIG probabilities, deterministic per seed) and re-rolls them on `restart` — bots' starting tyres adapt to the sampled weather (wet/intermediate in rain; **qualifying now models weather too** — `QualifyingEngine` takes a `weather` so the grid reflects race conditions, no more inverted rain grids) and bot **skill budgets scale player-relative** to the lobby (see `bots` block); `Lobby` in `src/lobby.ts` (Phase 4) owns the matchmaking queue + tick, grouping queued players by `division` into `Room`s and backfilling with bots. HTTP (non-WS) routes dispatch in `server.ts`'s `createServer` handler: `handleAuthRequest` (`/auth/*`, in `src/auth/http.ts`) then `handleApiRequest` (`/api/*` — first-login gate, training, **respec, skill-point allocation, leaderboard, stats, daily quests, weekly seasons, cosmetics/garage, soft currency**, in `src/api/http.ts`); shared CORS/sendJson/readJsonBody live in `src/http-util.ts`. **Prod hardening**: structured JSON logger (`src/logger.ts`), a real `/health` (DB `SELECT 1` ping + room/queue counts, 503 when DB down), and per-IP token-bucket rate limits on `/auth/*` (10/min) and `/api/*` (60/min) in `src/rate-limit.ts`; **graceful shutdown** via `SIGTERM`/`SIGINT` handlers (best-effort "сервер перезапускается" broadcast → `stop()` → 5s hard-exit fallback).
- `apps/web` — Vite + React + Canvas. **The game app, served at `/play/` in prod** (built with `BASE_PATH=/play/`). Renders snapshots only. **No game logic belongs here** (online/anti-cheat invariant). Design system: `src/tokens.css` (single source of truth — palette `--accent-red/green/orange/blue/purple/gold`, `--bg-primary/surface/elevated`, `--font-display` Rajdhani / `--font-mono` JetBrains Mono / `--font-body` Inter, loaded via Google Fonts in `index.html`) + base classes `.glass-panel`/`.neon-button`/`.ds-*` in `styles.css`. Race-specific styles in `src/race/race.css`. Screen flow: `onboarding (SetupScreen mode="onboarding") → hub → race`, driven by a state machine in `App.tsx` keyed off `authProfile.heroConfirmed`. The **Hub** (`src/HubScreen.tsx`) is a single map: raster background (`public/img/hub/hub-bg.png`) + 7 overlay building buttons (`public/img/hub/building-*.png`, AI-generated sprites with alpha) positioned in `%` over the bg via the `BUILDINGS` array; 6 training buildings wired to `/api/training/*`, the dominant race building → `onRace`. To reposition a building, edit its `x/y/w/h` in `BUILDINGS`. **Race UI** (`src/race/`): `TrackCanvas.tsx` renders 24×12 oriented cars (shadows + tyre-mark trails + brake sparks), Hammer Time glow, DRS zones, sectors, weather (rain particles/puddles/wet reflections) and time-of-day (sunset tint / night headlight cone) overlays, and per-trackId color palettes — it imports ONLY pure geometry/data (`trackById`/`TRACKS`) from the engine, never physics. `HammerButton.tsx` (3 mode chips A/D/P, available/active/cooldown states + keys 1/2/3, Shift=push) sends `{type:"hammerTime", mode}` and reads `CarSnapshot.hammerTime` (incl. `mode`) for its state. `TyreSelectScreen.tsx` is a 10-second pre-qualy overlay (shown once on lobby→qualy, gated on a non-empty `driverId` so it never flashes before matchmaking) with a weather card from the `welcome` forecast + compound buttons (soft/medium/hard always; intermediate/wet added in rain, with a recommended compound highlighted); on confirm or timeout it sends `{type:"setStartingTyre", compound}`, which the server applies to the hero's race starting tyre. `PilotStatsModal.tsx` is the read-only pilot view + an edit mode for respec (point-neutral redistribution). `LevelUpModal.tsx` pops on hub entry while `unspentSkillPoints>0` and spends them one-at-a-time via `/api/profile/allocateSkill`. `LeaderboardScreen.tsx` is the per-division leaderboard (tabs F1..F4) opened from the hub HUD. `apiBaseUrl()` (`src/identity.ts`) derives the **HTTP origin only** from `VITE_WS_URL` (which may carry a path — prod is `wss://f1-race.ru/ws`); it MUST strip the path or every API call lands on `/ws/...` and 404s. The WS connection uses `VITE_WS_URL` verbatim. **Game-feel layer**: `src/race/audio.ts` (synthesized Web Audio engine-RPM loop pitched by `hero.v` + one-shot DRS/hammer/pit-limiter/overtake stings, mute toggle in the topbar, respects `prefers-reduced-motion`); `TrackCanvas.tsx` has a **hero-cam** toggle (key `C`, 2.5× zoom/follow, auto-zooms-out in pits/pause) and an imperative `flashCar()` used by **overtake cinematics** (`RaceView.tsx` dispatches delta-encoded `events` — green flash + audio sting + "P5→P4" toast on a hero gain, red on a loss, gold "БЫСТРЕЙШИЙ КРУГ" on fastest lap, orange banner for `info`/DSQ/penalty events). **Race controls** also include `PushStrategySelect.tsx` (per-stint conservative/balanced/attack chips sending `{type:"setPushLevel"}`). **Onboarding/retention UI**: `SetupScreen.tsx` offers 3 archetype presets (Атакующий/Тактик/Универсал); `WeatherPitPrompt.tsx` fires a dismissible pit prompt on a mid-race dry→rain transition; a pinned `.dsq-warn` banner nags the hero who hasn't pitted in the last 2 laps; `QuestsPanel.tsx` (daily quests + claim), `GarageScreen.tsx` (cosmetics catalog/buy/equip — equipped `accentColor`/`carNumber` render on the hero car), `LeaderboardScreen.tsx` has a Сезон/Всё время toggle with a week countdown, and the Hub HUD shows the `softCurrency` wallet. Mobile: `@media (max-width:768px)` docks Pit+Hammer+Push to a thumb-reachable bottom bar; `--text-tertiary` alpha raised to 0.55 for WCAG AA; touch devices swap keyboard hints.
- `apps/landing` — Vite + React. **The marketing landing, served at `/` in prod** (root). Separate package so it can `import` the engine's pure geometry (`pathPointAt` etc. from `@f1race/race-engine`, aliased to source) for the live telemetry hero without pulling physics into the bundle (anti-cheat invariant preserved). ## Install gotcha (esbuild) — read this

`pnpm install` leaves esbuild's postinstall blocked → `ERR_PNPM_IGNORED_BUILDS` makes `pnpm install` and `pnpm <script>` wrappers return non-zero. `pnpm-workspace.yaml` carries an `allowBuilds.esbuild` toggle (and `onlyBuiltDependencies`); `.npmrc` has `verify-deps-before-run=false`. If scripts still exit non-zero, either set `allowBuilds.esbuild: true` in `pnpm-workspace.yaml` or just:

```
pnpm rebuild esbuild        # do this once
```

`better-sqlite3` is a native module too — it's already allow-listed in `pnpm-workspace.yaml` (`allowBuilds.better-sqlite3: true` + `onlyBuiltDependencies`), so `pnpm install` builds it from source (needs a C++ toolchain). Requires `better-sqlite3@13+` for Node 26 (no prebuilt binary; v11 fails to compile against Node 26's V8). If the native binding fails to load, `pnpm rebuild better-sqlite3`.

## Running it (two terminals)

```
pnpm --filter @f1race/race-engine build   # REQUIRED before server: it imports the engine via package exports -> dist/
pnpm --filter @f1race/server dev          # ws://localhost:8787
pnpm --filter @f1race/web dev             # http://localhost:5173 (game)
pnpm --filter @f1race/landing dev         # http://localhost:5174 (marketing landing)
```

- Always invoke dev scripts via `pnpm --filter <pkg> <script>` (runs in the package dir). The web `dev` script is bare `vite`; running `vite` from repo root 404s because `index.html` lives in `apps/web`.
- WS URL configurable via `VITE_WS_URL` (default `ws://localhost:8787`).

## Binaries are per-package, not at root

pnpm does not hoist `tsx`/`vitest`/`vite` to root `node_modules/.bin`. If `pnpm` wrappers misbehave, call the binary from the package, e.g. `apps/server/node_modules/.bin/tsx`, `packages/race-engine/node_modules/.bin/vitest`, or use `pnpm exec`.

## TypeScript strictness that will bite you

`tsconfig.base.json` enables `verbatimModuleSyntax`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`. In `race-engine` especially:

- Use `import type` for type-only imports.
- Never assign `undefined` to an optional field inline — build the object, then set the field conditionally. (Web/server tsconfigs relax `exactOptionalPropertyTypes` and `verbatimModuleSyntax`.)
- Indexing an array returns `T | undefined`; guard it.

## Tuning gameplay

Edit `packages/race-engine/src/config.ts`, then validate with a harness (keep seed count low — each run executes full races and gets slow):

```
pnpm --filter @f1race/race-engine sim          # one race, printed grid + result
pnpm --filter @f1race/race-engine sim:grid     # compare hero builds
tsx packages/race-engine/scripts/balance.ts    # avg finishing place across builds/seeds
tsx packages/race-engine/scripts/spread.ts     # P1→P20 time spread + neighbor gaps (balance of field)
tsx packages/race-engine/scripts/stretch.ts    # how the field spreads lap-by-lap (start "blob" debugging)
```

Spread of the field (no bunched pack, no giant mid-field holes) is tuned via per-driver `paceFactor` and `launchFactor` in `packages/race-engine/src/factory.ts` (gaussian, clamped). Goalpost: no single hero build or tyre combo is auto-win/auto-loss. `recommendedLaps(track)` derives lap count from a target race distance (not hardcoded).

## Conventions

- Comments: none in code unless a non-obvious formula/physics reason — keep it that way.
- Engine dt = 0.1s; server ticks ~10×/s. Both `solo` and `multiplayer` advance the sim at the room's `speed` (default `DEFAULT_SPEED=6` → ~6× real-time fast-forward). There is no real-time driving input in the protocol (only pit / hammerTime / startReaction — no throttle/brake) and the lights-out reaction is a separate real-time phase, so fast-forwarding the race is safe and keeps multiplayer pace equal to solo. Client `speed`/`pause` are still rejected in `multiplayer` (`activeConnectionCount >= 2`) — the pace is shared and one player can't change it for the room — but the default fast-forward applies.
- Reconnection: on disconnect a driver's slot (and car) is kept for `GRACE_PERIOD_MS` (default 30s, env-overridable for tests); `reconnect { sessionToken }` rebinds a new socket to the same driver. After grace the connection is evicted but the car keeps racing as an unowned ghost.
- **One live session per identity**: the `hello` handler rejects a fresh hello if the resolved identity (`guestId` for guests, `yandex:<id>` for OAuth) already holds a LIVE (`connected`) connection anywhere — queued in the lobby or in any room (e.g. the same account opening a second device/tab). Lingering grace-period sockets (`connected=false` after a drop) do NOT count, so a legitimate `reconnect`/re-enter after a dropped socket still works. This prevents one player from accidentally creating two connections (which would flip the room into `multiplayer` mode with a second human driver).
- No CI, no migrations/codegen (DB schema is `CREATE TABLE IF NOT EXISTS` + idempotent `ALTER TABLE … ADD COLUMN` guarded by `pragma table_info`, both in `sqlite-repository.ts` constructor). Git remote: `origin → https://github.com/rampage11/f1race.git`.
- **Pit/lap-time invariant**: pit-exit places the car at the next physical start/finish line + `pitExitS` (computed from `floor(car.s/length)`, NOT from `car.s - initialS` which is skewed by the negative grid `initialS` and previously teleported back-grid cars a full lap forward → bogus fastest laps = pit delta ~22-24s). Lap times are only recorded toward `bestLapTime`/`fastestLap` if within `[0.4×t0, 4×t0]` (defense against any remaining edge case). In rain, bot auto-pits pick a weather-appropriate compound (wet/intermediate), never dry slicks. **Auto-pit applies to BOTS only** — the hero pits ONLY on an explicit player `pit` request (player owns pit timing; never pitting → DSQ at the finish is the intended consequence). **Same-compound stops are allowed** (fresh rubber of the same type is a valid choice, e.g. fresh wets) but incur the 30s "didn't change compound" penalty; only a total failure to stop is a DSQ. The renderer's `pitPos` (TrackCanvas) ends the pit-lane animation at `exitPt` so the in→out transition is seamless (it previously ended at `entryPt` → visible teleport).

## Multiplayer protocol contract (Phase 1)

`apps/server/src/protocol.ts` is the canonical source. Current shape:

- `ClientMessage`: `hello { protocolVersion, hero, guestId?, authToken? }` (`guestId` = optional client UUID for persistence; absent → ephemeral. `authToken` = OPTIONAL Yandex OAuth session token issued by `POST /auth/yandex/callback` — when present AND valid it OVERRIDES `guestId`: the profile resolves by its `sub` (`yandex:<id>`); invalid/absent → graceful guest fallback. **`authToken` (Yandex identity) ≠ `sessionToken` in `reconnect`** (room-scoped reconnection).) | `reconnect { sessionToken }` | `restart` | `speed { value }` | `pause { paused }` | `pit { compound }` | `cancelPit` | `startReaction { clientTimestamp, sequenceId }` (Phase 2 lights-out mini-game; `clientTimestamp` is UX-only, fairness uses the server receipt time) | `hammerTime { mode: HammerMode }` (activates the driver's Hammer Time in one of `attack`/`defend`/`push`; server validates cooldown + block-conditions via `RaceEngine.requestHammer(driverId, mode)`) | `setStartingTyre { compound }` (pre-qualy tyre pick; server `Room.requestSetStartingTyre` validates the compound + that the stage is still `qualy`/`startSequence`, then overrides the hero driver's `startingTyre` when building the race grid; rejected once the race has started) | `setPushLevel { strategy: PushStrategy }` (per-stint push-level commitment — `conservative`/`balanced`/`attack`; server `Room.requestPushLevel` validates the strategy + rate-limit, forwards to `RaceEngine.requestPushLevel`, and re-applies the committed strategy after a pit stop since the engine resets to `balanced` on fresh-tyre exit) | `startTutorial { hero, guestId?, authToken? }` (parallel entry to `hello` for the guided first race — a client that sees `tutorialCompleted === false` sends this INSTEAD of `hello`; server resolves the profile, rejects if already `tutorialCompleted`, builds a `TutorialRoom` and streams `tutorialStep` hints).
- `ServerMessage`: `welcome { driverId, sessionToken, mode, profile?, track?, weather?, timeOfDay? }` (**Phase 4: now DEFERRED until the lobby matches the player; `profile: DriverProfileSummary` present only when a persisted profile was loaded/created. `welcome` is the lobby→room match signal — there is no separate "matched" message. It is also sent on `reconnect`, which bypasses the lobby. `track?/weather?/timeOfDay?` = the room's chosen race forecast (track `{id,name,country,lengthM,laps}`, `weather: Weather`, `timeOfDay: TimeOfDay`) so the lobby/qualy UI can render a forecast before the first race snapshot.**) | `lobbyState { division, queuedPlayers, estimatedWaitSec }` (Phase 4: unicast to a queued player on enqueue and on each match tick while they wait; `queuedPlayers` = humans currently waiting in the same division as the player) | `stage { stage }` | `snapshot { stage, snapshot, heroId }` (the race `snapshot` is the raw engine `RaceSnapshot`, which now carries `weather`, `effectiveWeather` (variable resolves mid-race), `timeOfDay`, `trackId`, `trackName`, `trackCountry`, and `eventSeq` (monotonic event counter — the server DELTA-ENCODES events per-connection: each client receives only events with `seq > conn.lastEventSeq`, so the `events` array no longer grows unboundedly on the wire; each `RaceEvent` carries `seq`); each `CarSnapshot` carries `hammerTime {active, mode, remainingSec, cooldownSec, readyAt}`, `drsActive`, `tow`, `pushStrategy` (the stint's `conservative`/`balanced`/`attack`), `lastLapTime`/`bestLapTime` (so the client renders lap times mid-race, not just in qualy)) | `result { result, heroId }` | `progression { xpGained, totalXp, level, xpIntoLevel, xpForNext, division, racesCount, streakDays? }` (unicast to each human connection with a profile, right after their `result` on finish — Phase 3) | `roomState { players, mode }` | `startSequence { lightsOutAt, sequenceId }` (broadcast when the lights-out sequence begins; `lightsOutAt` is a server wall-clock ms timestamp) | `startResult { driverId, reactionSec, jumpStart, category }` (unicast per player after resolution; `category: "perfect"|"good"|"slow"|"verySlow"|"jumpStart"` from engine `startCategory()`) | `tutorialStep { step, title?, text?, highlight?: "pit"|"hammer"|null }` (server-driven tutorial hint over the snapshot stream — the client renders a non-blocking overlay keyed off the stable step ids welcome/strategy_intro/pit_hint/hammer_hint/finish) | `error { message }`.
- `DriverProfileSummary = { guestId, hero: PilotProfile, level, division: Division, driverRating, heroConfirmed, totalXp, racesCount, tutorialCompleted, unspentSkillPoints }` (sent inside `welcome` and the `/auth/*` + `/api/*` responses). `tutorialCompleted===false` ⇒ the hub routes to the guided first race; `unspentSkillPoints>0` ⇒ the hub shows the Level-Up modal.
- `Division = "F4" | "F3" | "F2" | "F1"` (exported from `protocol.ts`). **Division + matchmaking are derived from the two-factor `driverRating`** (NOT bare `level`): `driverRating(level, skillSum) = level + (skillSum - startingPoints) * skillWeight` (weights in `config.ts` `driverRating` block), then `divisionForRating(rating)` (F4<10, F3 10-19, F2 20-34, F1 35+). For a fresh pilot `skillSum === startingPoints` so `rating === level` and F-boundaries are unchanged; trained skills can promote a pilot into a higher division without racing. This **resolves spec Q5** (`level` vs `skillSum`): both factors feed the rating, so idle training can't top the divisions without racing (it only boosts raw skill), and racing alone (bare `level`) can't move status as fast. `levelFromXp`/`divisionForLevel` still exist but `divisionForRating`/`driverRating` are what the lobby (`lobby.divisionOf`), `profileSummary`, and the `progression` message now use.
- Phase 3 persistence: profiles (SQLite via `better-sqlite3`, behind `DriverProfileRepository`) keyed by `guestId`; **profile resolution happens in the `hello` handler** (`resolveHeroProfile` exported from `room.ts`) so the lobby can read the player's `division` for matching — `Room.addConnection` accepts an already-resolved profile (5th `resolved?: ResolvedProfile` arg) and skips internal resolution when provided. Stored on `hello` (load/create), on race finish (`xpForRace` + one transaction = upsert profile + add race_history row), and on training completion (lazy, see below). DB path = env `DB_PATH` (default `./data/f1race.db`, WAL + synchronous=NORMAL); `apps/server/data/` is gitignored. No guestId → ephemeral (everything works, nothing persists). `DriverProfile` carries `heroConfirmed: boolean` (first-login gate), `freeRespecUsed?`/`lastRespecAt?` (respec gating), `tutorialCompleted?` (false ⇒ hub routes to the tutorial), and `unspentSkillPoints?` (banked from level-ups, spent via `/api/profile/allocateSkill`). **Brand-new Yandex users start with `heroConfirmed=false` AND `tutorialCompleted=false`** (both creation paths — `auth/yandex` callback and `resolveHeroProfile` — set them explicitly; the WS hello path detects `yandex:*` identities and forces the gate so a reset actually re-triggers onboarding). Level-ups accrue spendable points: `levelUpPointsAccrued(oldXp, newXp) = max(0, levelDelta) × pointsPerLevel`, applied in race-finish (`room.applyProgression`) and tutorial-finish (`markTutorialCompleted`). The schema is migrated idempotently in the repo constructor: `heroConfirmed`/`freeRespecUsed`/`lastRespecAt`/`tutorialCompleted`/`unspentSkillPoints`/`level`/`driverRating`/`division` columns (`ALTER TABLE … ADD COLUMN …` guarded by `pragma table_info`, legacy-safe defaults), plus the `trainings` table.
- **Onboarding gate + training + respec + leaderboard (Phase 5, onboarding/progression ТЗ)** — a separate HTTP channel (NOT WS), under `/api/*` in `src/api/http.ts` (Bearer `authToken`, same as `/auth/me`). `handleApiRequest(req, res, apiEnv)` returns `true` when handled, else falls through to health. Routes (all return `{ training: TrainingStateDto, profile: DriverProfileSummary, justCompleted?: {skill,newLevel} }` unless noted):
  - `POST /api/profile/confirm { hero }` — first-login gate: validates hero shape + `validateStartingAllocation`, sets `heroConfirmed=true`, upserts. 409 if already confirmed (no silent respec). The client forces `SetupScreen mode="onboarding"` until this is done.
  - `POST /api/profile/respec { skills }` — point-neutral skill redistribution (the new allocation must total the pilot's CURRENT skillSum, so it can't be farmed for free points). One free respec at level `respec.freeLevel` (=4), then a `cooldownDays` (=30) gate. 409 when locked below freeLevel or on cooldown; 400 on a non-neutral allocation.
  - `POST /api/profile/allocateSkill { skill }` — spends ONE banked level-up skill point on `skill` (clamped at `ABSOLUTE_SKILL_MAX`). 409 when no points / skill maxed. The hub's Level-Up modal calls this one point at a time.
  - `GET /api/training/state` — current status; **lazy completion**: if an active training elapsed (`startedAt+durationSec ≤ now`), it is resolved in a transaction (`+1` to `targetSkill` clamped to `ABSOLUTE_SKILL_MAX`, upsert profile, mark `completedAt`) and `justCompleted` is set.
  - `POST /api/training/start { skill }` — lazy-completes any elapsed training, 409 if one is still active, 400 if the skill is already at `ABSOLUTE_SKILL_MAX`, else inserts with `durationSec = trainingDurationSec(currentLevel, driverLevel)` (geometric growth: `baseDurationSec × growthFactor^level`; PLUS a per-driverLevel discount up to `levelDiscountMax` (−20%) so racing reinforces training — does NOT grant free skill points, so the `driverRating` idle-protection is preserved; **PLUS a fast start**: the first `training.fastLevels` (=3) trainings are a flat `fastBaseDurationSec` (=10min) instead of 30, to hook new players). One active training per account.
  - `POST /api/training/cancel` — deletes the active training (no partial progress; `cancelTraining` removes the row).
  - `GET /api/leaderboard?division=&limit=&season=current` — **public** (no auth required, so it's shareable): top profiles in a division by `driverRating` (denormalized `level`/`driverRating`/`division` columns on `profiles`, computed on every upsert so the top-N query ORDER BYs an index). `division` defaults to the viewer's; `limit` clamped [1,100]. Returns `{ division, rows[], me? }` where `me` is the viewer's own rank (computed via a COUNT-ahead query) when authed. **`?season=current`** scopes to the current Monday-start UTC week (helper `seasonWeek(ts)` in `src/season.ts`), ranking by weekly `xpGained` summed from `race_history`; the response then also carries `season: {label, weekStart, weekEnd, resetAt}` for a client countdown.
  - `GET /api/stats` — **authed** (the viewer's own): a single SQL aggregate over `race_history` → `CareerStats {totalRaces, wins, poles, podiums, bestFinish, averagePlace (excluding DNFs), dnfCount, totalXpGained}`.
  - `GET /api/quests/state` — **authed, 403 if `!heroConfirmed`**: lazy-assigns today's 3 daily quests (idempotent, seeded by `(profileId, UTC day)` from the static catalog in `src/quests.ts`) if none assigned yet today, returns `{quests: [{questDefId, desc, goal, progress, claimed}][]}`.
  - `POST /api/quests/claim {questDefId}` — awards `xp` + `softCurrency` if `progress>=goal` and not yet claimed; 409 otherwise. Returns updated `{quests, profile, claimed:{questDefId,xp,currency}}`. Quest progress is incremented server-side in `applyProgression` on race finish (`finish_race`, `finish_top5`, `overtakes_2` via positionsGained, `pit_stop`, `fastest_lap`) and in `/api/training/start` (`start_training`).
  - `GET /api/cosmetics/catalog` — **public**: static catalog from `src/cosmetics.ts` (`[{id, type:"accentColor"|"carNumber", value, cost, level}, ...]`), cosmetic-only (no gameplay effect).
  - `GET /api/cosmetics/owned` — **authed**: `{owned: string[], equipped:{accentColor?, carNumber?}, softCurrency, profile}`. Equipped stored as a JSON column `equippedCosmetics TEXT` on `profiles`.
  - `POST /api/cosmetics/buy {unlockId}` — validates level gate (403) + `softCurrency` balance (402) + not-already-owned (409); deducts + inserts into `unlocks(profileId, unlockId)`. Returns the owned shape.
  - `POST /api/cosmetics/equip {unlockId}` — validates owned (403); updates `equippedCosmetics` JSON. Returns the owned shape. The web client applies equipped `accentColor`/`carNumber` to the hero car in the renderer.
  - 403 on the training/respec/allocate/quests/cosmetics routes if `!heroConfirmed`; 401 if no/invalid bearer.
  - `TrainingStateDto = {status:"idle"} | {status:"active", skill, startedAt, durationSec, remainingSec}`. No background ticker — completion is computed on each `/state` (and `/start`) hit.
- **Soft currency + streak** — `profiles` now carries `softCurrency INTEGER` (earned on every race finish in `applyProgression`: `min(100, 10 + 5×(fieldSize−place))`, 0 on DNF; plus quest claims) and `lastRaceDay`/`streakDays` for a consecutive-day-login XP bonus (`+10%` per streak day, cap `+60%` at 7 days; same-day race = no extension). `DriverProfileSummary` carries `softCurrency` so the hub shows the wallet. `progression` carries optional `streakDays`.
- **Phase 3 Yandex OAuth** (`apps/server/src/auth/`): authorization-code flow implemented directly in Node (NOT Supabase like align360). Routes are added to the existing `createServer` HTTP handler in `server.ts` (extended; no Express). `handleAuthRequest(req, res, env)` returns `true` when handled (auth route), `false` → falls through to the default health JSON. Routes:
  - `OPTIONS *` → 204 with CORS headers (`Access-Control-Allow-Origin` from env `ALLOWED_ORIGIN`, default `*`; allow-headers `content-type, authorization`; allow-methods `GET, POST, OPTIONS`).
  - `POST /auth/yandex/callback` — JSON body `{ code: string, redirectUri: string }`. Validates presence → token exchange (`POST https://oauth.yandex.ru/token`, `application/x-www-form-urlencoded`, body has `grant_type=authorization_code & code & client_id & client_secret & redirect_uri`) → user info (`GET https://login.yandex.ru/info?format=json`, header `Authorization: OAuth <access_token>`). Profile key = `yandex:<id>`, loaded/created via `DriverProfileRepository` (reuses the same `profiles` table). Brand-new user gets `DEFAULT_YANDEX_HERO` with `heroConfirmed=false` (forces the onboarding gate; flipped by `POST /api/profile/confirm`). (`apps/server/src/auth/yandex.ts` — mirrors `apps/web/src/race/SetupScreen.tsx` `DEFAULTS`; **keep them in sync**). Issues a stateless **session token** (HMAC-SHA256, see below) and responds `200 { sessionToken, profileSummary: DriverProfileSummary, isNewUser }`. Token-exchange failure → 502 `{ error }`; missing fields → 400; Yandex creds unset → 503 `{ error: "yandex oauth not configured" }`.
  - `GET /auth/me` (optional convenience) — `Authorization: Bearer <sessionToken>` → returns the `DriverProfileSummary`. Missing/invalid token → 401; profile gone → 404; `SESSION_SECRET` unset → 503.
- **Session token format** (`apps/server/src/auth/session.ts`): `base64url(payloadJson) + "." + base64url(hmac)`, where payload = `{ sub: "yandex:<id>", iat: Date.now() }` and hmac = `HMAC-SHA256(SESSION_SECRET, base64url(payloadJson))`. Stateless, no DB lookup to verify. Constant-time compare via `crypto.timingSafeEqual`. `verifySessionToken(token, secret)` returns `{ sub, iat } | null` (never throws — WS hello handler falls back to guest on null). Returns null when `secret` is empty (auth disabled).
- **Auth env vars** (graceful degradation when unset):
  - `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` — from https://oauth.yandex.ru/client/new (scopes `login:email login:info`, redirect URIs include `http://localhost:5173/yandex-callback` for dev + prod `https://<domain>/yandex-callback`). NEVER sent to the client; used only in the `/auth/yandex/callback` exchange. State-param CSRF is handled CLIENT-side (mirrors align360's `sessionStorage` state); the server exchanges whatever code it receives.
  - `SESSION_SECRET` — random string for HMAC. If Yandex creds are set but this is unset → `startServer()` throws. If unset AND no Yandex creds → server boots, `/auth/yandex/callback` returns 503, WS runs in pure-guest mode.
  - `ALLOWED_ORIGIN` — already existed; reused for CORS on auth responses (default `*`). WS does not need CORS.
  - `PUBLIC_BASE_URL` — canonical origin (optional); not currently used since the client sends `redirectUri` explicitly.
- `Stage = "qualy" | "startSequence" | "race" | "finished"`. `"startSequence"` (Phase 2) sits between qualy and race: qualy finished, the lights-out reaction window is open, the `RaceEngine` is not yet built. Reconnecting players are re-sent the current `startSequence`.
- `RoomMode = "solo" | "multiplayer"`, derived live from `activeConnectionCount >= 2`; exposed in `welcome` and `roomState`.
- Commands that can't apply return `{ type: "error", message }` rather than no-op (pit outside race, multiplayer speed/pause/restart, rate-limit hits). Same-compound pits are NOT an error (allowed, but penalized 30s at the finish). Rate limits (per connection): `pit`/`cancelPit` 1500ms, `restart` 10s (and solo-only — rejected in multiplayer), `pause`/`speed` 500ms, `hammerTime` 300ms (the engine cooldown is the real gate; this just prevents spam), `setStartingTyre` 800ms, `setPushLevel` 300ms.
- **Phase 4 lobby** (`src/lobby.ts`): `Lobby` owns a queue of `{ connectionId, sink, guestId, hero, savedProfile, division, enqueuedAt }` entries and a matchmaking tick. Tuning constants (env-overridable): `MATCH_TICK_MS` (default 30000 — spec Фаза 4 "тик 30с"), `SOLO_WAIT_MS` (default 2000 — a lone player past this with no same-division company matches into their own bot-filled room), `MAX_WAIT_MS` (default 60000 — widener: a player past this matches into ANY division rather than waiting forever). `enqueue()` sends `lobbyState` and runs an immediate group-only pass (≥2 same-division humans → same room); solo fast-start fires on the tick. Tests set `MATCH_TICK_MS=50`, `SOLO_WAIT_MS=0`, `MAX_WAIT_MS=1000` (in `tests/helpers.ts`) so a lone player matches within ~one tick. `Room.__advanceForTest({ stopAtRace? })` is a test-only seam that drives a room synchronously to race/finish (reaching a real race takes minutes); it reuses the same private step methods the production tick uses.

## Gameplay systems (Hammer Time / weather / tracks)

The race simulation now models several spec features; all tuning is in `packages/race-engine/src/config.ts`.

- **Hammer Time** (`HAMMER_TIME` block): the single active ability, in **3 strategic modes** (`HammerMode = "attack" | "defend" | "push"`, picked by the player at activation). `RaceEngine.requestHammer(driverId, mode)` validates and returns `HammerRequestResult = "activated" | "rejected_cooldown" | "rejected_pit" | "rejected_first_lap" | "rejected_tyre_wear" | "rejected_unknown_driver" | "rejected_not_racing"`. Validation order: phase → driver → pit → first-lap lock (`car.lap >= 2`) → tyre wear (`< minTyreWearToActivate`, 0.60) → cooldown (`engine.time >= car.hammerReadyAt`). On success sets `car.hammerMode = mode`, `car.hammerActiveUntil = time + durationSec` (8s) and `car.hammerReadyAt = time + durationSec + cooldownSec` (45s → ~53s gate-to-gate). While the boost window is open the car gets that mode's multipliers: **attack** (cornering ×1.08, overtake ×1.45, defense ×1.0, tyreWear ×2.4), **defend** (cornering ×1.12, overtake ×1.0, defense ×1.50 — makes the car HARDER to pass, inverting the old ×0.8 defender penalty into an intentional mode), **push** (cornering ×1.18, overtake ×1.10, defense ×1.0, tyreWear ×4.0). The `tyreWear` multiplier is applied proportionally to the fraction of the lap the boost was active, using the PERSISTED `car.hammerMode` — so a boost that expires mid-lap still taxes wear for the time it ran (the step-local mode would already be null at lap completion). The server `Room.requestHammer(connectionId, mode)` maps the union to error strings. State is in the snapshot per car as `hammerTime { active, mode, remainingSec, cooldownSec, readyAt }` (remainingSec reports the *current* phase — boost time while active, else cooldown time, else 0). The web `HammerButton.tsx` shows 3 mode chips (A/D/P, keys 1/2/3, Shift=push) when available, each firing `{type:"hammerTime", mode}`, and renders state from the snapshot (anti-cheat: client never decides readiness).
- **Weather** (`weather` block): `Weather = "dry" | "lightRain" | "heavyRain" | "variable"`. `tyres.intermediate`/`tyres.wet` compound entries exist alongside soft/medium/hard. `gripFor(tyre, weather?)` and `wearDeltaForLap(tyre, km, mgmt, weather?)` apply `weather.gripMultiplier[weather]` and per-compound `compoundWeatherGrip`/`compoundWeatherWear` maps (dry compounds penalized in rain; wet/intermediate penalized in dry). Overtake probability scales by `weather.overtakeMultiplier[weather]` (rain = more overtakes). **`variable`** is resolved by the engine into `effectiveWeather` (dry until the leader reaches `ceil(totalLaps/2)` then lightRain); the snapshot carries BOTH `weather` (scheduled) and `effectiveWeather` (currently in effect — render rain from this). `compoundForWeather(weather, rng)` (server) picks bots' starting tyres (wet/intermediate in rain). Weather probability comes from `weather.probability` in CONFIG.
- **Time of day** (`timeOfDay` block): `TimeOfDay = "day" | "sunset" | "night"`, cosmetic only (no physics). Carried in the snapshot as `timeOfDay`; the web renders a sunset orange tint or a night darkening + hero headlight cone + red tail-glow dots. Probability from `timeOfDay.probability`.
- **Tracks** (`src/track.ts`): 3 factories — `redBullRing()` (4.318 km, 12 laps, 3 DRS zones), `monza()` (5.793 km, 9 laps, 2 DRS), `interlagos()` (4.309 km, 12 laps, 1 DRS). Each `path2D` is a **dense (~120-point) polyline of REAL surveyed geometry** from `TUMFTM/racetrack-database` (OSM-derived smoothed centerlines, `tracks/*.csv`) reproducing the actual circuit in the correct direction of travel (Monza = two huge straights + Parabolica; Interlagos = counter-clockwise valley bowl) — the canvas renders them with a Catmull-Rom smoothing spline + per-track scenery. **Each centerline is rotated so `path2D[0]` = the start of the main straight (the real start/finish line)** — this anchors `s=0` (S/F line, start grid, `pitEntryS`≈0.97L / `pitExitS`≈0.03L, sector splits) to the correct physical spot (without this the arbitrary OSM start point put the pits/grid mid-corner). `segments` (corner/straight + `targetSpeed`/`overtaking`) are **derived from the real curvature profile** by `scripts/gen-tracks.ts`, which emits `src/track-data.ts` (the committed generated data — `RED_BULL_DATA` / `MONZA_DATA` / `INTERLAGOS_DATA`). Registry: `TRACKS: Track[]`, `TRACK_FACTORIES`, `randomTrack(rng)`, `trackById(id)`. Track ids: `red_bull_ring` / `monza` / `interlagos` (note underscores). Each `Track` carries `drsZones: {startS, endS}[]` (s in meters) and `sectors: number[]` (two s-values → 3 sectors). The server picks one track per room — the room's `seed` is **randomized at construction** (so different rooms open on different tracks; previously a constant `42` made every fresh room start on the same track) and re-rolled on `restart`. (Monaco was tried from `julesr0y/f1-circuits-svg` but removed — the SVG conversion didn't render well enough; only the 3 TUMFTM tracks remain.)
- **DRS + slipstream**: `TrackSegment.overtaking` (0..1) drives the overtake ease; `battle.drsPassMultiplier` (1.20) boosts passProbability when the attacker is in a DRS zone within `battle.drsGapSec` of the car ahead (`car.drsActiveUntil` is set, exposed as `CarSnapshot.drsActive`). `slipstream` block (`gapSec 2.0, paceBonusSec 0.25, minOvertakingScore 0.3`) grants a small tow bonus when close behind on an overtaking-friendly segment (`CarSnapshot.tow` flags it for the renderer).
- **Start categories** (`startCategory()` in `formula.ts`): `StartCategory = "perfect"(0–0.15s) | "good"(0.15–0.35s) | "slow"(0.35–0.60s) | "verySlow"(>0.60s) | "jumpStart"`. The engine's `computeStartOutcome` already applied `perfectBonusAccel`/launch debuffs internally from `reactionTimeSec`; `startCategory()` just labels the UX band and is sent in `startResult.category`.
- **Race control contract**: the player controls pit + Hammer Time (3 modes) + the lights-out reaction + a **per-stint push-level commitment** (`setPushLevel {strategy:"conservative"|"balanced"|"attack"}`) during a race. No throttle/brake input, no manual DRS (auto in zones) — explicitly out of scope per the spec's headline constraint. The push-level is a *strategic* input (same category as compound choice / Hammer mode), NOT real-time driving input: the player commits a strategy for the stint, the engine applies it to cornering pace + tyre wear, and resets to `balanced` on fresh-tyre pit exit (the server re-applies the committed strategy post-pit). Pit timing is the player's alone (bots auto-pit; the hero never auto-pits). Same-compound stops are a permitted-but-penalized choice.

## Capacity baseline

`pnpm --filter @f1race/server load-baseline` — measures per-tick wall-clock and RSS across 1/10/50/100 rooms (2 conns each, multiplayer pacing). Findings in `docs/load-baseline.md`: ~0.033 ms/room race-tick, 100 rooms = 3.3 ms/frame (of a 100 ms budget) → single-process + periodic Redis snapshot (P10) is adequate through hundreds of rooms; no worker isolation needed for Фазы 1–4. **Note:** that measurement predates the Hammer Time / weather / DRS / slipstream / **per-stint push-level / event-seq delta-encoding** systems (small per-car-per-tick additions; the `eventSeq` work is per-snapshot, and quest/currency progression runs once at race-finish, not per-tick) — conclusion still holds, but re-run `load-baseline` before scaling beyond a few hundred rooms.
